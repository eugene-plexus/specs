## The first qualification, and what it found

The first candidate (specs `93eef94`, tag commit `277c6e2`) failed
[Release qualification 39191972022](https://github.com/eugene-plexus/specs/actions/runs/39191972022):

- **Workbench's own tests were red at MR9b (`e254256`).** MR9b raised the store
  to schema 21 and added the connections setting; nine tests still expected
  schema 20 and the old settings list. Workbench's CI had failed on that commit
  and Edge published it anyway, because Edge's receipts are the specs CI's. The
  fix is test-only (`5ee5644`); the Workbench runtime did not change.
- **The agent's Windows tests that need pywin32 ran without it.** Qualification
  installed `.[dev]`; every Windows install carries the `service` extra. The
  workflow now installs the agent's shipped extras. With them, the agent's full
  suite passed on Windows 11: 2,662 passed, 21 platform skips, no failures. The
  agent's own CI runs its tests on Linux only.
- **Workbench's full Windows suite ran past the 30-minute job limit**; the limit
  is now an hour.
- **The new upgrade harness's agent would have checked GitHub for updates**
  (the S10 instruments check, specs#19); it now turns update checks off.
- **c3's S2** (a speech clip through the gateway) failed once on Windows with
  no error in its report. It passed on Linux in the same run and on both
  platforms in the full-profile CI above, with the same Workbench runtime. Its
  report now carries the job's error. Recorded as intermittent and unexplained.

## Upgrade from v0.2.3

**Windows 11, in place, with a person's data**
(`scripts/release-upgrade-acceptance.py`, new for this release): **30 of 31
checks passed; the one failure was the harness's.**

1. v0.2.3's own installer (from the `v0.2.3` tag) installed into an isolated
   prefix. The root was set up, the node enrolled, a second person (`morgan`)
   created in control, and Workbench `bccae98` (store schema 17) installed from
   v0.2.3's catalogue.
2. Through v0.2.3's own APIs, the operator signed in to Workbench and created a
   titled chat with a real exchange with the seeded model, a pinned memory
   note and an uploaded Markdown document.
3. The agent stopped cleanly; the candidate installer ran over the same prefix;
   the candidate agent started on the same configuration. All seven component
   commits then equal the manifest.
4. The agent did not move Workbench to the new catalogue version by itself
   (checked for 60 s); `POST /v1/apps/workbench/install`, the console's app
   update, updated it. The store migrated from schema 17 to 21 and kept
   `workbench.sqlite3.schema-17.bak`.
5. Control sign-in worked without re-initializing; `morgan` is still listed;
   the operator signed in to Workbench as the same person. The chat title and
   both messages, the note (id, text, kind, pinned) and the document (record,
   original bytes by SHA-256, extracted text) came back identical. A new
   message on the old chat got a reply from the model.
6. The live service and the account's `EUGENE_PLEXUS_*` environment were
   unchanged.

The failed check compared the installed Workbench with `9f51391`, written into
the harness for the first candidate. The installed Workbench was `af67506`,
the version the candidate's catalogue names (packaged install above). The
check now reads the expected version from the candidate's catalogue; that
corrected check has not been run.

`-Isolated` refuses an existing prefix, and the other in-place routes
(`-Update`, or a plain run that writes the account-wide config variable) are
unusable beside this machine's live service. The harness therefore runs the
candidate installer with that one guard removed, asserting it matched once;
everything else is the shipped text. The Windows `-Update` path itself
(scheduled task, service refresh, tray) was not exercised.

The first candidate's run of the same harness passed 31 of 31 against
Workbench `9f51391`, whose runtime is identical to `af67506`'s. Evidence:
`docs/private/release-evidence/v030b-3-upgrade.log` and
`%TEMP%/ep-v030-upgrade-2/result.json`; the first run's
`v030-windows-upgrade.log` and `%TEMP%/ep-v030-upgrade/`.

**Ubuntu under WSL2, Linux system install, the in-app update path**
(`scripts/updates-system-install-acceptance.sh`, `EP_FROM=v0.2.3`,
`EP_TARGET=b60c7c9…`, as root): **all checks passed in 32 s.** v0.2.3 made a
system install; the update was requested through the request file the app's
route writes and carried out by the root-owned helper; the agent that came back

## Untested paths and limits

- **The root container upgrade** (Troy's NAS case) was not run here; this
  machine has no Docker. Release qualification and the container workflow run
  Compose, installed-Workbench and recovery acceptance on the versioned image,
  not an upgrade of a v0.2.3 container volume.
- A root with standbys and workers upgraded in order, and mixed-version
  refusal, were not exercised in a packaged install; U3's record covers the
  refusal with development code.
- Windows `-Update` and the Windows service/tray update, macOS packaged install,
  native Linux unattended boot, any GPU in a packaged install, Intel Arc, two
  physical cards and the container on a passed-through NVIDIA card.
- The second person did not sign in after the upgrade; only their directory
  entry was checked. Going back to v0.2.3 by restoring Workbench's copy was
  not tried.
- Live Google and Microsoft sign-in; a real Claude Code, Codex or Open WebUI
  connected to Workbench's MCP server.
- Strata and MLX remain experimental; Strata's native image inference is
  unvalidated.
- Feature limits are in the release notes, [v0.3.0](../releases/v0.3.0.md).
