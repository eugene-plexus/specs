## Upgrade from v0.2.3

**Windows 11, in place, with a person's data**
(`scripts/release-upgrade-acceptance.py`, new for this release): **31 of 31
checks passed.**

1. v0.2.3's own installer (from the `v0.2.3` tag) installed into an isolated
   prefix. The root was set up, the node enrolled, a second person (`morgan`)
   created in control, and Workbench `bccae98` (store schema 17) installed from
   v0.2.3's catalogue.
2. Through v0.2.3's own APIs, the operator signed in to Workbench and created a
   titled chat with a real exchange with the seeded model, a pinned memory
   note and an uploaded Markdown document.
3. The agent stopped cleanly; the candidate installer ran over the same prefix;
   the candidate agent started on the same configuration. All seven component
   commits then equal the manifest.
4. The agent did not move Workbench to the new catalogue version by itself
   (checked for 60 s); `POST /v1/apps/workbench/install`, the console's app
   update, updated it to `9f51391` in about 160 s. The store migrated from
   schema 17 to 21 and kept `workbench.sqlite3.schema-17.bak`.
5. Control sign-in worked without re-initializing; `morgan` is still listed;
   the operator signed in to Workbench as the same person. The chat title and
   both messages, the note (id, text, kind, pinned) and the document (record,
   original bytes by SHA-256, extracted text) came back identical. A new
   message on the old chat got a reply from the model.
6. The live service and the account's `EUGENE_PLEXUS_*` environment were
   unchanged.

`-Isolated` refuses an existing prefix, and the other in-place routes
(`-Update`, or a plain run that writes the account-wide config variable) are
unusable beside this machine's live service. The harness therefore ran the
candidate installer with that one guard removed, asserting it matched once;
everything else is the shipped text. The Windows `-Update` path itself
(scheduled task, service refresh, tray) was not exercised.

Evidence: `docs/private/release-evidence/v030-windows-upgrade.log`,
`%TEMP%/ep-v030-upgrade/result.json` and `seeded-state.json`.

**Ubuntu under WSL2, Linux system install, the in-app update path**
(`scripts/updates-system-install-acceptance.sh`, `EP_FROM=v0.2.3`,
`EP_TARGET=93eef94…`, as root): **all checks passed in 28.6 s.** v0.2.3 made a

## Untested paths and limits

- **The root container upgrade** (Troy's NAS case) was not run here; this
  machine has no Docker. Release qualification and the container workflow run
  Compose, installed-Workbench and recovery acceptance on the versioned image,
  not an upgrade of a v0.2.3 container volume.
- A root with standbys and workers upgraded in order, and mixed-version
  refusal, were not exercised in a packaged install; U3's record covers the
  refusal with development code.
- Windows `-Update` and the Windows service/tray update, macOS packaged install,
  native Linux unattended boot, any GPU in a packaged install, Intel Arc, two
  physical cards and the container on a passed-through NVIDIA card.
- The second person did not sign in after the upgrade; only their directory
  entry was checked.
- Live Google and Microsoft sign-in; a real Claude Code, Codex or Open WebUI
  connected to Workbench's MCP server.
- Strata and MLX remain experimental; Strata's native image inference is
  unvalidated.
- Feature limits are in the release notes, [v0.3.0](../releases/v0.3.0.md).
