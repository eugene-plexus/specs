# Eugene Plexus v0.7.0

This release brings operations rights for people who are not the owner, team knowledge and shared projects in Workbench, the prompt cache kept on disk across restarts, and routing by predicted time to first token. It includes all completed work since v0.6.0.

Versioned Windows and POSIX installers, a component manifest, the Python dependency lock and checksums are available in the [GitHub release](https://github.com/eugene-plexus/specs/releases/tag/v0.7.0).
The Linux amd64 container is `ghcr.io/eugene-plexus/control-plane:v0.7.0`.

**Update the root and its standbys first, then every gateway.** See [Updating](#updating).

## Operations rights for people who are not the owner

The owner can now let a person run machines without being the owner. On a person's Administration access, there are two new powers:

- **Models:** download, delete and re-scan models, edit profiles, and create, start, stop, restart and change runtimes.
- **Updates and restarts:** update Eugene and engines, install and remove engine builds, restart components, and read the machine's logs.

Each power can be limited to chosen machines. Any power also lets the person read machines, runtimes, models, host history and health issues.

The person signs in through the administration sign-in and chooses **Open the console**. They see only the pages their powers use. For each machine, the console gets an operations token from the root. The token is for that one machine and lasts 10 minutes. The machine's agent, library and gateway accept it only on the routes the power opens. A test sends a token that holds every power to every gated route.

What stays the owner's: provider keys and other secrets, people's chats, sign-in keys and the passphrase, enrolling and removing machines, Job Sites, routing and backends, client keys, folder access, pause and resume, **Update all**, and delegating powers. No combination of powers sees everything. With an operations token, a runtime or profile may not set environment variables, the working directory, the program, extra arguments, an address other machines reach, or a file outside the Library's folders. The refusal names the field. Reads with the token show no environment values or extra arguments.

Each machine keeps a record of who changed what, for 90 days and at most 10,000 rows. The owner reads it on the machine's page. The person in each row comes from the verified token. The owner's own changes are in it. Refused and failed attempts have their own cap of 1,000 rows, so they never push out a change.

Behaviour changes:

- **Directory routes need a directory grant.** `/v1/people`, `/v1/permission-groups` and `/v1/oidc/clients` now answer only the owner and a person with a people, groups or membership grant. Before, any named administrator could read them. A person with operations powers only gets a 403.
- **Refusals say who may.** A valid operations token on an owner's route gets a 403 "Only the owner can do this" from the agent, library and gateway. The inference driver is unchanged and still answers 401.

Limits:

- A removed power or a sign-out ends the person's tokens at once on a machine that can fetch the trust bundle. In CI, that took 0.0 to 0.5 s. A machine that cannot fetch it may accept a token for up to 15 minutes (the token's 10, and 5 that every verifier allows for clocks that disagree). The delegation editor says so.
- Only the owner reads the record.
- CI ran the acceptance on real Linux and Windows. It runs the exchange, the gates, the record and the revocation, and a sabotage check that fails when a route is put in the table by mistake. On one host, a machine's proxy refuses another machine's loopback address, so the check for the strip toward a second machine is an agent unit test and not part of the acceptance.

## Team knowledge and shared projects in Workbench

**Team collections.** The owner of a Workbench makes a collection, for example "Acme handbook", and gives it to people or groups as **Read** or **Contribute**. A chat or project with the collection attached searches it beside the person's own documents and memory. Answers cite it as "Acme handbook: Onboarding.pdf". The check runs on every search, from the person's current groups.

**Shared projects.** A project's owner shares it with people or groups. They get its instructions and shared notes, and its documents. They start their own chats in it. **Chats are never shared.** The owner sees a count of other people's chats and never their content. A member who loses access loses the project's knowledge at the next search. Their chats stay theirs and are detached from the project.

Notes in a collection are never kept automatically. A model may propose one with `suggest_team_note`. The person sees and approves the words first. The note then waits in the inbox until a contributor accepts it. A shared project's collection takes no notes. A contributor cannot replace another person's document of the same name.

Calls built as defaults, which move or delete documents that other people added:

- **R47-DELETE.** Deleting a shared project with "delete everything" deletes its collection, including members' documents. With "keep", every document in it, members' too, moves into the owner's My documents. Removing a shared project's owner deletes the project's collection, including members' documents. The dialogs say how many documents other people added.
- **The first share moves data.** The first share with people moves the project's uploaded documents from the owner's index into the project's own collection index. Chats do not move. A move cut short answers 503 and says to share again.
- **R47-PICKER.** The owner sees everyone in the share picker. Anyone else sees only people who share a group with them.
- **R47-OUTSIDE.** Each collection has **Outside models may read it**, off by default. Its manager sets it. When it is off, a cloud or unplaced model gets nothing from the collection, and the chat says why.
- **When a person is removed,** what they added stays in the collection, marked "Added by a former member". The owner can delete it. Their unaccepted proposals, grants and shares go.

Limits:

- Only the owner of the Workbench makes install collections and grants. A group's manager cannot yet, because the manager grant does not reach Workbench in the sign-in claims.
- A shared project shares only notes that are marked shareable, and its documents. Documents read from a project's folders stay the owner's.
- Scanned pages in a collection are not read. The page says the document was skipped.
- CI ran the acceptance on Linux and Windows with a stand-in model backend: 64 of 64 checks, with a sabotage check that cuts out the grant check and must fail. No real cloud model read a collection.

## The prompt cache kept on disk

Before Eugene stops or restarts a llama.cpp model on purpose, the agent now saves what each slot holds of its chat. When the model is next ready, the agent reads the newest files back before it reports `ready`. The next turn of each chat then does not reread its whole prompt. Planned stops are Stop, idle unload, a model switch, a settings edit, a drain and the agent stopping. A crash saves nothing.

**Chats are kept somewhere new.** The files hold the token ids and the engine's state for every person's chats. They are in the agent's private folder, `prompt-cache`, beside its settings. No route serves them. The console shows counts and sizes only. Eugene deletes them when:

- you turn **Keep the prompt cache on disk across restarts** off (it is on by default);
- you choose **Delete saved conversations** on the machine's settings;
- a file is older than **Delete a saved conversation after (days)** (3 by default, counted from the save), or the folder is over **Use at most (GiB)** (20 by default, oldest first);
- you delete the runtime;
- you uninstall and choose "Also delete settings, app data and logs".

A save never takes the disk below **Always leave at least this much free (GB)** (10 by default). A Windows or Mac move of the install does not carry the folder. An engine update is a new key, so the first start on a new build reads nothing back. A changed command line or model file does the same. Only a llama.cpp runtime that listens on loopback saves. A runtime with `--no-slots` or an API key saves nothing, and its note says why.

With llama.cpp's default slots, a stop keeps only the last chat. The engine moves idle slots to a RAM cache that cannot be saved. On b12428, three chats gave one file. Set a slot count on the profile, or pin slots, and each slot keeps its chat. Whether the cache should force that by default is open (R15-SLOTS). It is not done, because it changes how the engine shares memory.

Measured on a CPU (llama.cpp b12428, this PC): with Stories15M, 72 tokens reused after read-back. With LFM2-350M, a hybrid model, 69 of 73 tokens reused (9.8 ms after read-back, 58 ms cold). A save and read-back took under 0.1 s for 1 to 2 MiB. CI ran the same checks on Linux and Windows with a real llama.cpp CPU build and Stories15M. A second model reviewed it. Not run: any GPU, and any large model. The GPU numbers in the design are not measured. The gain on a GPU is unknown.

## Routing by predicted time to first token

This applies to a model served by more than one replica.

**A conversation waiting for its own replica moves when another is predicted to answer sooner.** The gateway measures each runtime's peak prefill rate in tokens/s from its served requests, and its mean answer time. A conversation moves only when rereading its whole prompt on another replica is predicted to be at least **Extra wait before a conversation moves** (2,000 ms by default) sooner than waiting. A short turn moves at once. A turn with a long history waits. A runtime has a rate after 8 requests that read at least 256 uncached tokens. Until then the conversation behaves as with the setting off. The setting **Move a conversation when another replica answers sooner** is on by default. Off, a pooled-context conversation waits for its replica, and any other goes at once to a replica with a free slot.

**`spread` now places new conversations by the tokens a replica holds.** The order is the share of context held (in 5% steps), conversations per slot, expected wait, then load. A runtime that reports vLLM's `/load` adds that to its load. It is on by default. **Place new conversations by the tokens a replica holds** turns it off and restores the earlier order: conversations per slot, then requests in flight. `least_busy` and `round_robin` are unchanged. A replica that does not report its context makes the order fall back to conversations.

Not run on hardware. Two arithmetic tests (short and long turns, and an eight-replica spread) checked placement. The cache-balancing measurement on real replicas did not run. Prefill rates are not fitted to prompt and cache size, and Workbench shows no wait message.

## Other changes

- **Hindsight database password:** the agent made the password with a URL-safe generator. When it began with `-`, the database program read it as a flag and Hindsight never started. This happened for about one install in 64. The agent now makes it again until it does not begin with `-`, and replaces a kept one that does. No database holds such a password. The failing log hides the password, so the cause comes from the error and the start command.
- **Supplied TLS certificate:** the agent now reads a certificate or key you supplied again when its content changes, not its modification stamp. Windows stamps writes with a coarse clock, so a certificate renewed in place could wait for the next stamp change. Agent#45.
- **Console fonts:** the console's fonts now come from the package. The build no longer fetches them from Google, so it works with no network and no longer fails when Google does not answer. Ui#28.

## Updating

Update in this order:

1. **The active root and every standby.** An older root has no operations token exchange. An older standby cannot apply a person record that has an operations power, and keeps asking the root for a full copy until it is updated. Update standbys before the owner gives anyone an operations power.
2. **Every gateway.** An older gateway answers 401 to an operations token and has neither new routing setting.
3. **Every other machine**, with **Machines → Versions → Update all**. An older agent or library answers 401 to an operations token, so update every machine in a person's scope before you give them a power.
4. **Workbench**, which needs a separate app update. Update all includes it; otherwise update it from **Apps**. It holds team knowledge.

Containers update through Docker or their NAS controls; pull the v0.7.0 image.

The Workbench store moves from schema **34 to 35** in place on first start. It adds tables and changes none that exist. Before it moves, Workbench keeps a copy of the whole store beside it as `workbench.sqlite3.schema-34.bak`. Workbench v0.6.0 refuses a schema 35 store and leaves it as it is. To go back, restore the copy with matching software. The gateway's request-metrics store stays at schema **15**, and the store component stays at schema 2. Back up a stopped installation; see the [installation and recovery guide](https://eugeneplexus.com/install/#update).

The prompt cache starts empty. It fills at the first planned stop of a llama.cpp model.

The previous [v0.6.0 release limits](v0.6.0.md) still apply.
