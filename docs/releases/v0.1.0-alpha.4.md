# Eugene Plexus v0.1.0-alpha.4

The fourth public alpha. It remains a **prerelease**: not a stable release, and
not a claim of production readiness. Start with the
[installation guide](https://eugeneplexus.com/install/).

**alpha.3 upgrades in place.** Run the installer again, the same one-line
command, and it keeps your passphrase, models, client keys and joined machines.
From alpha.4 on, each machine can be updated from the console. An alpha.2 install
still needs a fresh install; see [Moving to alpha.4](#moving-to-alpha4).

## Changes since alpha.3

### Every graphics card the machine has

- **Eugene now sees every GPU the operating system lists**, AMD, Intel Arc and
  integrated graphics included. alpha.3 found an Intel Arc machine's engine
  build and then scored every model against its system memory, reporting
  "no GPU".
- **The engine build matches the card.** A machine with no NVIDIA card gets
  llama.cpp's Vulkan build. Snapdragon, Linux AMD without ROCm, Linux Intel,
  Windows with oneAPI and NVIDIA GB10 each get the build that uses their card.
  Where a card is left unused, Eugene names it. **Other builds** on the
  Inference page picks a different one.
- **One model can span several cards:** two of the same vendor, or an NVIDIA
  card beside an AMD or Intel one on Windows. A launch is scored against the
  memory of the cards it will use together, not the largest one alone.
- **The Visual C++ runtime llama.cpp needs is installed with Eugene.** On a
  freshly installed Windows machine without it, every model in alpha.3 crashed,
  with no reason shown. A Windows crash code is now named in words.

### Updates from the console

- **Nodes → Versions shows what each machine runs**, whether a newer version is
  out, and an **Update** button. It works from any console: update a worker from
  the NAS page. Each machine checks a minute after it starts and every six
  hours, and installs only when you press Update.
- **Two channels:** `releases`, the newest published release, and `edge`, the
  newest commit on which every check passed. A machine follows the one it was
  installed from, and **Config → Agent → Updates** changes it.
- **A container is told how to update in its own platform's words:** Unraid's
  Force Update, `docker compose pull`, or re-pulling the image with the same
  folders. A container pinned to a release is told to change its tag first.
- **Issues** names a machine with an update waiting, an update that failed (in
  its own words), and machines on different versions.

### Every machine's log, from the console

- **A Logs page**, like `docker logs`. On the install it shows every machine on
  one timeline; under a machine, that machine alone. It covers each agent and
  every service and model it runs, and follows live.
- **Filter** by source or text, choose how many lines, and **Download** for a
  bug report. Keys and tokens are hidden.
- **Each model on Inference links to its engine's own lines:** "what its engine
  said" when it stopped or crashed.

### While a model is working

- **The wait says what the model is doing:** how much of the prompt llama.cpp
  has read, that a hosted backend is working, and which tool Claude Code or
  Codex is running. A reasoning model's thinking is shown as it arrives.

### Library folders

- **After you change a folder's mount or a machine's override, the page lists
  the running models still on the old file**, with one **Restart** for them
  all. Nothing needs a reboot.
- **A machine that cannot read the Library's folders says why.** Its column
  turns red with the reason. When the model then cannot start, the refusal says
  the folders were unread, instead of asking for a mount you already set.

### Fixes

- **Start on a model whose load failed starts it again.** Before, it answered
  "already running; nothing to do", and only Restart worked.
- **An update keeps the port its install uses.** Without this, re-running the
  Windows installer over a service on another port would have moved the service
  to 8079.

## Verification and limits

- **The exact pins passed** Windows and Linux CI, the Pester installer suite,
  and container acceptance before the image was published.
- **The packaged installers passed a clean install** on Windows and in WSL, as
  recorded in the [release record](../acceptance/alpha4-release-run.md).
- **Upgrading alpha.3 in place**, on a Linux system install in WSL: alpha.3's
  installer, then this one run over it. The passphrase set before still signed
  in, and an in-app update then ran through its root helper.
  The [updates record](../acceptance/updates-run.md) covers the rest.
- **Updating from the console on Linux** runs in CI on every commit. It starts
  from the previous commit's installer and updates to the new one; the first
  real version change moved three components. **The Windows paths have not run
  for real:** the service as SYSTEM, and a per-user install.
- **Logs** were read and followed live between two agents, through the
  machine hop, with a real engine failing to load. See the
  [logs record](../acceptance/logs-run.md).
- **GPUs:** measured on an RTX 5090 beside an integrated AMD Radeon, including
  Vulkan inference on the Radeon. **An Intel Arc card has not run it yet.** See
  the [every-GPU](../acceptance/every-gpu-run.md) and
  [two-card](../acceptance/two-cards-run.md) records.
- **Still owed:**
  - an Intel Arc card;
  - two physical cards in one machine;
  - models on a passed-through NVIDIA card in the container;
  - a physical Mac;
  - modest-GPU capacity;
  - native Linux unattended boot;
  - the Windows reboot-before-sign-in checks;
  - moderated sessions with people new to Eugene.
- Use a trusted LAN or VPN, and finish first-run setup before enabling remote
  access.

See the [support matrix](../support-matrix.md) for each promise and its
evidence.

## Moving to alpha.4

- **From alpha.3: run the installer again**, the same command you installed
  with. It stops Eugene, replaces its packages and starts it again, keeping
  everything else.
  - Windows:
    `irm https://eugeneplexus.com/releases/v0.1.0-alpha.4/install.ps1 | iex`
  - Linux or macOS:
    `curl -fsSL https://eugeneplexus.com/releases/v0.1.0-alpha.4/install.sh | sh`

  Do this on every machine. From then on, **Nodes → Versions** updates each one
  from the console.
- **The container:** select `ghcr.io/eugene-plexus/control-plane:v0.1.0-alpha.4`
  and keep the same data folder. An existing Unraid container shows general
  Docker steps until `EUGENE_PLEXUS_CONTAINER_HOST=unraid` is added on its Edit
  page, because Unraid does not add new template fields to an existing
  container. **Set Config → Agent → Advertise address** to the address you type
  in the browser, port included: a worker needs it to reach the Library.
- **From alpha.2:** a fresh install, as the
  [alpha.3 notes](v0.1.0-alpha.3.md#moving-from-alpha2) describe, then install
  alpha.4.

A recovery checkpoint made on alpha.3 restores alpha.3.

## Distribution

The [GitHub prerelease](https://github.com/eugene-plexus/specs/releases/tag/v0.1.0-alpha.4)
provides `install.ps1`, `install.sh`, `manifest.json` and `SHA256SUMS`.
- **The tag** is annotated and immutable.
- **The manifest** records the specs commit and all six component commits, the
  built UI export included. That export's join commands name the alpha.4
  installer, so a worker installs the version its root runs.
- **Each component knows its own commit.** GitHub stamps it into the source
  archive the installer downloads, and Nodes → Versions reads it back.

The Linux amd64 image is built from the tag and published only after container
acceptance passes. Its digest is added to these release notes on GitHub.
Earlier alphas' tags, assets, containers and website installer URLs remain
available.

These pins fix Eugene's source, not every upstream dependency: Python packages,
uv, engine downloads and model catalogue data can change.
