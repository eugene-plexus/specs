# Eugene Plexus v0.5.0

This release brings macOS services in Eugene's own account, program approvals, Workbench skills, preview recovery, machine diagnostics, a limit on frozen trust, stored API conversations, and app recovery fixes. It includes all completed work since v0.4.0.

Versioned Windows and POSIX installers, a component manifest, the Python dependency lock and checksums are available in the [GitHub release](https://github.com/eugene-plexus/specs/releases/tag/v0.5.0).
The Linux amd64 container is `ghcr.io/eugene-plexus/control-plane:v0.5.0`.

**Update the root and its standbys first.** See [Updating](#updating).

## macOS services and machine labels

New macOS installs run Eugene as a system daemon in its own hidden account, as Linux system installs do. It starts before anyone signs in. Installation needs administrator access. A protected passphrase file lets it unlock at boot.

Keep models in `~/Eugene Models` or another folder the account can read. macOS privacy rules restrict Desktop, Documents and Downloads. Job Sites on a Mac still require a per-user install with `--user`. Physical Mac reboot, sign-in, Metal and privacy-prompt checks remain unrun.

Both installers accept a label when joining: `--label` on POSIX and `-Label` on Windows. Machines has a **Shown as** field that adds it to the join command. The flag requires a join. Windows labels cannot contain a double quote or end in a backslash.

## Program approvals

On macOS daemon and Linux system installs, the console asks before Eugene's account runs an engine program that one other account can change. Only the owner can approve it. Approval applies to one file. A change to its contents, ownership or path permissions requires approval again.

The approved program runs with Eugene's account access. Approving it trusts the account that can change it. Eugene refuses programs with paths writable by a group or others. Eugene also refuses programs whose checked paths have more than one other owner. The console names the cause and offers Eugene's own build. Settings lists approved programs with **Remove**.

## Skills in Workbench

Add skills from **Toolbox → Skills** by uploading a ZIP or `SKILL.md`, or write one on the page. Read, edit, disable or delete them there. The model sees enabled skills' names and descriptions. It can load instructions and reference files when needed.

Uploaded and replaced skills start off. Review their instructions before turning them on. Skills written on the page start on. The install owner can give a skill to everyone. It appears as **From Eugene**, enabled by default. Each person can disable it.

Chat settings can use all enabled skills, selected skills or none. The list has a limit of 32 skills and 8,000 characters of names and descriptions. The page explains omissions. Skill scripts require a Job Site that allows commands and follow that site's approval rules.

## Preview recovery in Firefox and Safari

If a preview started but did not report finishing before the page closed or reloaded, Workbench asks for **Run** when it next appears. Other previews still follow the chat's automatic-run setting. A corrected revision can run automatically too.

The first loop can still freeze the chat. Close the tab to recover. An unfinished run is evidence, not proof of a loop. The guard needs browser storage and does not catch loops that begin after the first run finished. Chrome and Edge keep their existing behavior. Checks used Firefox and WebKit. Real Safari and iOS remain unchecked.

## Machine addresses and versions

Machines and Home now show why the root refused a machine's address announcement. The message names the cause and the next step. A move onto the open internet still requires re-enrollment. Refusal details clear when the root restarts and return when the machine retries.

Each machine's card shows its release, Edge build date, development status or failure to match a published release. **Details** shows component commits. The navigation tree's footer shows the version of the machine serving the console. Older agents may show no version. An older Edge build that was never matched can read **not a published release**.

## Encrypted machine connections

In automatic machine TLS mode, managed components with a machine table hold requests to machines the table does not yet know. They send no install token there over plain HTTP. Known older machines without a machine port can still use HTTP. Standalone processes without a table keep their existing behavior. HTTP Job Site invitations remain unencrypted.

If another program holds port 8083, the machine stays unreachable from other machines until the port is free. Eugene no longer reaches it in clear. Its card names the program holding the port.

## Trust during a root outage

After 24 hours without contact with the root, a machine refuses changes authorized by other machines' keys. Home reports this state. Root-issued sessions and the machine's own tokens still pass. Running models can still answer with valid credentials. Another machine cannot wake a stopped model after the limit. Client keys still need the root for admission.

The expert setting `maxTrustBundleAgeHours` changes the limit; 0 disables it. Enforcement needs a pinned encrypted connection to a remote root. Local loopback also qualifies. Without that channel, the limit is not enforced, and the setting says so.

## Stored responses and conversations

The OpenAI-compatible Responses API now keeps input, output, model and token usage for people and client keys by default, including when `store` is omitted. Apps can continue with `previous_response_id`, retrieve or delete responses, and list their input items. Apps can also create conversations and manage their items.

Responses stay for 30 days by default. Continuing a chain extends its earlier links to the newest response's expiry. Conversations stay until deleted. Storage belongs to the person or client key. The install owner sees counts, not content. Rotating a client key does not transfer access to its stored history.

`store: false` keeps no response. When a request names a conversation, its input and output still enter that conversation. Deleting a response from the middle of a chain breaks later continuations. Instructions do not carry forward through `previous_response_id`. Model context limits still apply.

In **Settings → Store**, experts can disable response storage or change retention. A conversation retention limit applies to existing conversations too, counted from last use. Disabling storage stops new saves and continuations. Existing records remain readable and deletable until expiry.

## App recovery

On Windows, **Go back** after a failed app update now runs the retained old version. Windows' queued crash restart can no longer replace it with the failed version. Recovery still restores the saved data copy and loses changes made after it.

On Linux, an app kept running across an agent restart no longer remains marked **starting** forever.

## Updating

Update in this order:

1. **The active root and every standby.** An older root refuses signed address announcements containing the new `machineError` field. Machines send it while their machine port does not answer. The address-refusal, trust-limit and version additions do not add incompatible request fields.
2. **Every other machine**, with **Machines → Versions → Update all**.
3. **Workbench**, which needs a separate app update. Update all includes it; otherwise update it from **Apps**.

Containers update through Docker or their NAS controls; pull the v0.5.0 image.

Workbench migrates its database from schema **33 to 34** on first start. It keeps `workbench.sqlite3.schema-<N>.bak` beside it, where N is the previous schema. It refuses a newer schema.

The store component migrates schema **1 to 2** automatically on start. It keeps `store.sqlite3.schema-1.bak` before adding response and conversation storage. Existing files remain. It also refuses a newer schema. Going back requires matching software and data. Person removal purges their data from migration copies too. Back up a stopped installation; see the [installation and recovery guide](https://eugeneplexus.com/install/#update).

A normal Mac update keeps its LaunchAgent. To move to the daemon, run the installer again without `--update` or `--user`. The move keeps identity, port, Library state and settings, but clears some executable paths and reports them. Sign in with the passphrase once afterward. Eugene downloads engine builds and reinstalls catalogue apps again. Added apps need manual reinstallation. The old installation stays in an administrator-only folder until Eugene is removed. Existing program approvals do not cross the move.

Stopped Windows app services now show **Disabled** in `services.msc`. Eugene enables them when preparing a start.

If you roll a machine back to software from before machine ports, remove it and join it again. Announcements no longer clear its recorded machine port.

The previous [v0.4.0 release limits](v0.4.0.md) still apply.
