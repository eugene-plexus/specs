# Eugene Plexus v0.7.1

This release brings models and routing per permission group, usage and money allowances, dashboards and alerts for administrators, and vLLM from its official container image. It includes all completed work since v0.7.0.

Versioned Windows and POSIX installers, a component manifest, the Python dependency lock and checksums are available in the [GitHub release](https://github.com/eugene-plexus/specs/releases/tag/v0.7.1).
The Linux amd64 container is `ghcr.io/eugene-plexus/control-plane:v0.7.1`.

**Update the root and its standbys first, then every gateway and agent.** See [Updating](#updating).

## Models and routing per permission group

On a group's page, under Policies, there are two new settings:

- **Models:** "All models", or a list of model names. An entry may hold `*` (at most 8; a name over 256 characters never matches).
- **Routing by role:** for each role, the install's list, or an ordered list of 1 to 16 models.

The gateway checks every model a person's request reaches: the model asked for, each fallback, and the models the server-run image tool calls. `GET /v1/models` lists only the allowed models. A model a group leaves out gets a 403 `model_not_allowed`: "Your group Sales does not include m3. Ask the owner, or choose another model." A role with no allowed model left gets a 404 that names the role. A key with no person (Open WebUI's shared key, Claude Code) gets the install's routing and its own list, as before.

**The active group decides routing only.** A person in several groups has an active group. A role resolves through the active group's list, less the models the person may not reach. A role the group does not route uses the install's list, filtered. Model limits come from **every** group the person is in that sets a list: a model must be in all of those lists. A group with no list adds no limit. Choosing a group never widens what the person reaches. Leaving a group widens it at their next request. This is call R37-SELF, Choice 3, built as the default. The person's page shows each list and its group. Changes reach the person's next request, not the next token refresh. A request waiting in the gateway's line is refused when it leaves the line. A change to a person's model lists also ends their running requests at the next lease renewal (409). A routing change does not.

Behaviour changes:

- **Group writes keep a policy they leave out.** Inside `policies`, a policy left out keeps its value, and `null` clears it. In v0.7.0 a left-out policy was cleared. A v0.7.0 console, which sends only the policies it knows, no longer clears a group's routing and models on save.
- **The sign-in claim is unchanged.** `eugene_policies` carries only the v0.7.0 policies, so an older Workbench still signs people in. Apps read routing from the gateway.
- **A route to a model outside the group's own list is a 422** that names the model.

Limits:

- The owner sets a person's active group on the person's page ("Works with"). A person sets their own at `POST /oidc/active-group`, at most once a minute (429 `slow_down`, with `Retry-After`). A delegated administrator may not set it. Neither the console nor Workbench has a picker for the person yet (workbench#24).
- CI ran the acceptance on real Linux and Windows with three fixture drivers that serve chat only, so the role it checks is `role:agentic`. A sabotage check skips the person's list inside the gateway's process and must fail. A second model reviewed it. Its blocker, a slow request body that wrote back an old person record, is fixed.

## Usage and money allowances

A key or a group can have a token allowance per UTC day, a token allowance per UTC month, and a money allowance per month. A request over an allowance is refused before it runs. A request that crosses the line while it runs finishes, and the next is refused. The refusal is OpenAI's own for a spent quota: 429, `insufficient_quota`, a sentence that says which allowance, how much was used and when it resets, and `Retry-After`. The Anthropic door says `rate_limit_error` and the Gemini door `RESOURCE_EXHAUSTED`. When a token allowance is spent and the request names a model, the root refuses it on arrival, so it never waits in a line. Counting is install-wide. The control root counts every gateway's requests for the key (across rotations), the person and their groups. A group's allowance is one pool for its members. A person in several groups is refused only when every group that sets that kind of allowance has spent it. A stream that ends without the engine's count, or a caller who leaves, counts an estimate, marked `estimated`.

**The owner sets a price for each served model** on the new **Usage** page: dollars per million tokens in and out. Eugene has no built-in price table. The price of a request comes from, in order:

1. the owner's rate;
2. the price the provider reports (an OpenRouter account's listing);
3. nothing, for a model that all its backends serve locally: it is free until the owner sets a rate;
4. otherwise it is unknown. Unknown is counted as unpriced, never as free, and a money allowance refuses it and says why.

A new rate counts from the next request. Past requests keep their cost. Eugene does not estimate electricity, hardware or connection costs. Money is exact: the root counts whole pico-dollars, and the API says dollars as a 12-place decimal string.

The Usage page shows tokens and cost per key, group and person, by day and month and by model, with the allowances and what is left. A person sees their own usage in Workbench Settings (**Your usage**) and sees their groups' totals without other members' per-model counts.

Behaviour changes and data:

- **Key and group writes keep an allowance they leave out.** `null` clears it. This holds for key limits and for every group policy.
- **A cloud fallback with no price** inside a request admitted on a priced model is priced as the admitted model. Routing does not skip such a fallback under a money allowance.
- The root keeps each subject's newest 62 days and 13 months of use, at most 32 models a period (the rest under `*`). A deleted key, person or group keeps its counters, at most 75 periods. Counting adds no log entries.
- A standalone agent, with no root, refuses an allowance and says why.
- CI ran the acceptance on Linux and Windows with two gateways and a fixture backend, with a sabotage check that drops one gateway's counts. Not run: a comparison with a real provider's bill.

## Dashboards and alerts

**Dashboards** shows every machine together, what waking each model costs (starts, how long people waited, and an energy estimate: the wait times the machine's GPU power), and how each SLO stands. **Metrics** gains 30 and 90 days, and **Hosts** gains 90 days. Hours rolled up before this release have a wake wait of 0, and the page says so.

**Alerts** shows what fired and resolved, the rules, the SLO targets and the webhook. The active, unlocked control root evaluates once a minute. A standby does not. The alert state is not replicated: a root that takes over starts empty and fires again what still holds. Until the owner saves rules, five built-in rules apply, and they show on Home only: a machine down for 5 minutes, a disk over 90% for 10, a GPU over 85 °C for 5, failures over 5% over 10 minutes (at least 10 requests), and an SLO burning 14.4 times too fast for 5.

An SLO targets a model or a client key: a success share, or a first-token percentile (p50, p90 or p99), over a window of up to 90 days. A key's SLO has success only. The owner alone sets rules, targets and the webhook. A person with an operations power reads the alerts and SLOs for machines in their power's reach, and for models.

The **webhook** is off until the owner sets it. Eugene posts JSON (`rule`, `state`, `value`, `threshold`, `machine`, `model`, `url`, `at`, and `text` and `content` for Slack, Discord and ntfy), tries three times, and then shows "The alert webhook did not answer" with the cause on Home. The address is sealed, and only its host is shown back. It is in no log. Once it is set, alert lines (machine names, model names, values) leave the install for that address.

Limits:

- The webhook ran only against stand-ins. No real Slack, Discord, ntfy or Home Assistant service received a post.
- The root reads the gateway through its own machine's agent. When two other machines run a gateway, it reads neither and names both.
- "Keep loaded" links to the machine's backends. It does not change the setting, because the change restarts a running runtime.
- CI ran one acceptance step on Linux and Windows: on four machines, the root reads a third machine's gateway through the first machine's proxy. Unit tests cover the rules, the webhook and the views.

## vLLM from its official container image

Where Docker or Podman can use the GPUs, Eugene runs each vLLM runtime in the official image. On Windows it uses Docker Desktop with WSL 2 and an NVIDIA GPU. The Engines page shows what it found, for example "Docker 27.3.1, GPUs available", or the reason it cannot be used, with the fix. Eugene in a container has no Docker socket and does not ask for one, so it cannot run this.

- **The image is pinned by digest per release:** vLLM 0.33.0 (CUDA 13), vLLM 0.32.0 for CUDA 12 drivers, and AMD's `rocm/vllm` 0.29.0, labelled untested. The pull is large (several GB), runs as an engine install with progress, and happens only when you ask on the Engines page, or install and start a vLLM model there. A runtime start never pulls. The image in use and the one before it are kept.
- **A runtime start:** the model folder mounts read only. The port binds to loopback unless the profile names a host. Shared memory is `--shm-size` (8 GiB by default, set in the profile), never `--ipc=host`. Environment values stay off the command line. The compile cache is kept per runtime and removed when the runtime is deleted. A tokenizer outside the model's folder is refused.
- **Stop** is `docker stop -t 30`. At each agent start, Eugene removes every container labelled with its own agent before any runtime starts. A container is left behind only when the agent's whole process tree is killed at once, or on Windows when the job object ends the CLI. The next start removes it.
- **The default source** is the container when an image is pulled, a container runtime can be used and no vLLM program is set. "Use my own vLLM" stays. An operations token may set `source` and `shmSizeGiB`, not the image.

Data facts:

- **An image that was on the machine before Eugene is never removed.**
- Uninstalling vLLM removes the images Eugene pulled, and a third pull removes the oldest, each by its recorded ID. An uninstall that cannot remove an image answers 409 after vLLM is gone, names the image and keeps its record. Uninstall again to retry.
- On Docker Desktop, GPU memory for vLLM reads "unknown" with the reason, not 0.

Not run: real vLLM in its image on a GPU. CI ran the acceptance on Linux only, with a CPU fixture image (9 checks), and reached the engine on its own port, not through a gateway. The Windows and Docker Desktop path, ROCm and SELinux relabelling of the model mount are untested. On the row's final CI, three macOS jobs (A4 on macOS 15, offline removal on macOS 15 and 26) never got a runner. Their result is unknown.

## Other changes

- **Tokenizer path:** an operations token could point vLLM's `tokenizer` outside the Library's folders on a native runtime. It is now refused, and the refusal names the field. Agent#48.

## Updating

Update in this order:

1. **The active root and every standby.** Control's replicated log is now version 4 (alerts 2, allowances and prices 3, groups 4). An older standby cannot apply the new entries. The root refuses these writes with 409, naming the standby, until it is updated: alert rules and the webhook, an allowance, a model price, a group's routing or model list, and a person's active group. A v0.7.0 policy still saves.
2. **Every gateway and every agent.** An older agent or gateway answers 503 to a person whose groups set routing or model limits. It never serves a request outside their models. An older gateway's requests are not counted toward allowances, and a money allowance refuses them as unpriced unless the owner set a rate.
3. **Every other machine**, with **Machines → Versions → Update all**.
4. **Workbench**, which needs a separate app update. Update all includes it; otherwise update it from **Apps**. It holds **Your usage**. Its store stays at schema **35** and does not move.

Containers update through Docker or their NAS controls; pull the v0.7.1 image.

The gateway's request-metrics store moves from schema **15 to 16** in place on first start and keeps its history. It makes no copy first. A v0.7.0 gateway sets a schema 16 store aside as a `.v16.bak` file beside it and starts fresh, and the history stays in that file. The store component stays at schema 2. Back up a stopped installation; see the [installation and recovery guide](https://eugeneplexus.com/install/#update). No image is pulled by the update. Alerts, allowances, prices and group settings start empty.

The previous [v0.7.0 release limits](v0.7.0.md) still apply.
